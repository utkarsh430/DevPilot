# DevPilot evals — Promptfoo + LLM-as-judge

Phase 1 / M12. The eval harness for DevPilot's role prompts. Source-of-truth doc:
`docs/DEVPILOT_PHASE1_PLAN.md` §M12.

## What's in this directory

| File                          | Purpose                                                                                                                                                                                                                                                        |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `promptfooconfig.yaml`        | Root config; lists every role under test. Documentation-only — the runner walks `*.eval.yaml` directly.                                                                                                                                                        |
| `<role>.eval.yaml`            | Per-role Promptfoo config: provider pinned to `claude-sonnet-4-5-20250929`, `temperature: 0`, system prompt loaded from `snapshots/<role>.system.txt`, 2-4 fixture tickets, assertions = regex / substring / `llm-rubric`.                                     |
| `snapshots/<role>.system.txt` | Frozen body of each role's **stored** `systemPrompt` - the bare role prompt, without the layers the dispatcher composes on top at runtime. Regenerated by `snapshot-prompts.mjs`. Both the YAML and the snapshot must change together when a prompt is edited. |
| `baseline.json`               | Committed snapshot of per-role pass-rates on `main`. CI fails a PR if any role drops > 5 pp vs this. Updated by a maintainer; see "Updating the baseline" below.                                                                                               |
| `candidates.jsonl`            | Append-only stream of failed-run signals from the production engine. NOT auto-promoted — operator triages weekly. See "Candidate gold set pipeline" below.                                                                                                     |
| `snapshot-prompts.mjs`        | Regenerates `snapshots/*.system.txt` from the live role source files. `--check` for CI verification mode. The role list is **derived** by parsing `lib/roles/index.ts` — adding a role there adds its snapshot automatically. See "Snapshot coverage" below.   |
| `run-acceptance.mjs`          | M12 acceptance script — proves the harness detects a deliberate regression. See "Acceptance" below.                                                                                                                                                            |

## How a role is evaluated

Each role yaml uses Promptfoo's Anthropic provider, pinned to a fixed Sonnet
model ID with `temperature: 0`. The system prompt body is loaded from
`snapshots/<role>.system.txt` via `file://` so the on-disk snapshot is the
load-bearing artifact. Each test case is a fixture ticket payload
(title / description / acceptance_criteria / prior_comments) and a small
set of assertions:

- **Structural** — `regex`, `contains`, `not-icontains` against the role's
  documented output shape (e.g. PM's `Title:` / `Description:` /
  `Acceptance Criteria:` block, Triage's `next: <key>` line).
- **State-machine** — for roles that decide a ticket transition (QA), the
  expected `status: "done" | "in_progress"` is asserted in the output.
- **LLM-as-judge** — a `llm-rubric` block evaluated by the same pinned
  Sonnet, scoring the response against a written rubric.

### What the snapshot does _not_ contain

`snapshot-prompts.mjs` reads each role's stored `systemPrompt` straight off its
`RoleConfig`, so a snapshot is the bare role prompt.
The prompt an agent actually sees on a live ticket has up to two more fenced
sections appended by `composeRoleSystemPrompt`
(`apps/web/lib/roles/compose-prompt.ts`) at dispatch time: the
**reviewer-awareness note** (for ticket-bound runs of any role whose
`onSuccessStatus` is `in_review`) and the **installed-skill fence** (tenant-installed
skill bodies selected for that ticket).
Neither is persisted, so neither belongs in a snapshot, and editing either one
leaves `--check` green.
Their gating, ordering, and idempotence are pinned by Vitest instead
(`apps/web/lib/roles/__tests__/`), not by these snapshots.

## Snapshot coverage — why the list is derived, not written

`snapshot-prompts.mjs` used to carry a hardcoded 11-role object under a
comment claiming it walked "the live ROLES map … with no risk of drift". It
had drifted: 42 of the 53 roles in `lib/roles/index.ts` had no snapshot,
including `backend_engineer` and the ~9.5KB `project_scaffolder` prompt that
makes a new project's entire stack decision. A prompt edit to any of the 42
was invisible to CI.

The list is now derived from `lib/roles/index.ts` itself. It cannot be
imported directly — `index.ts` pulls every role through the `@/lib/...`
tsconfig path alias, which does not resolve under bare
`node --import tsx` from the repo root — so the script parses that file's
imports and its `ROLES` map statically, then imports each role module by
relative path (every role file's own imports are `import type` only, so each
loads standalone). **Adding a role to `index.ts` now adds its snapshot with
no other action.**

Any parse failure, unresolvable entry, or implausibly short list (under
`MIN_EXPECTED_ROLES`) is fatal rather than skipped — a silently shorter role
list is the exact failure this replaced.

One role sits outside that map: `supervisor` casts its slug at the union
boundary and is not registered in `ROLES`, but has a committed
`supervisor.eval.yaml`. It is listed in `EXTRA_ROLES` with that reason.

## Running locally

```bash
# 1. Refresh snapshots from the live role files (after any prompt edit).
node --import tsx tests/evals/snapshot-prompts.mjs

# 2. (Optional) Verify snapshots are current — CI does this too.
node --import tsx tests/evals/snapshot-prompts.mjs --check

# 3. Run one role's eval (Promptfoo needs ANTHROPIC_API_KEY in env).
cd tests/evals
pnpm --filter @devpilot/web exec promptfoo eval -c qa.eval.yaml

# 4. Run the M12 acceptance script (deliberate regression detection).
cd ../..
pnpm --filter @devpilot/web exec node tests/evals/run-acceptance.mjs
```

## Acceptance — `run-acceptance.mjs`

Per `docs/DEVPILOT_PHASE1_PLAN.md` §M12:

> Introduce a deliberate regression (loosen QA's REJECT criteria); CI
> catches it.

`run-acceptance.mjs` does this in four steps:

1. Asserts snapshots are in sync (`snapshot-prompts.mjs --check`).
2. Runs Promptfoo against `qa.eval.yaml` with the **current** QA prompt;
   captures `baseline.passRate`.
3. **Hot-swaps** `snapshots/qa.system.txt` with a loosened variant: the
   FIRST-PASS-REJECT policy paragraph is replaced with a permissive
   "approve if reasonable" instruction. The yaml's `file://` reference
   picks up the new body without any other change. The original snapshot
   is backed up to `.qa.system.txt.bak`.
4. Re-runs Promptfoo with the loosened prompt; captures
   `loosened.passRate`.
5. Asserts `baseline - loosened > 5 pp` (the same threshold CI uses).
6. **Always** restores the original snapshot in a `finally` block, even
   on test failure.

The choice of prompt-swap over `var` injection is deliberate:

- It exercises the same `file://snapshots/...` loading path as CI.
- New roles automatically inherit the regression-test capability.
- The diff between original and loosened snapshots is exactly the artifact
  CI would surface in a PR comment if the role were edited.

## Updating the baseline

**A role whose `pass_rate` is `null` does not block a PR.** `ci-compare.mjs`
treats it as bootstrapping, records the live number, and exits 0. So while
the baseline is all-`null`, the only hard gate on a prompt change is
`snapshot-prompts.mjs --check` — a mechanical "was this file regenerated"
check, not a quality check. Recording real numbers is what arms the gate.

```bash
# from repo root, with ANTHROPIC_API_KEY set, on a clean tree
node tests/evals/run-acceptance.mjs --record-baseline
```

This runs every `*.eval.yaml` once and writes each role's pass-rate, plus
the ISO timestamp and the HEAD commit, into `baseline.json`. It refuses to
run in two cases, both deliberate:

- **No `ANTHROPIC_API_KEY`** — recording zeros from a suite that never ran
  would arm the gate against a fiction, which is worse than leaving it
  disarmed.
- **Dirty working tree** (override with `--allow-dirty`) — `recorded_commit`
  is the claim that these numbers describe the prompts at that commit.

Re-record after any deliberate prompt change that legitimately moves a
pass-rate, and state the recorded commit in the PR.

### CI also needs the key

`ci-compare.mjs` exits 0 with a `note:` line when `ANTHROPIC_API_KEY` is
absent — it skips every role rather than misreporting an unrunnable suite
as a regression. That means **a recorded baseline alone does not make CI
block**: the `evals` workflow reads the key from
`secrets.ANTHROPIC_API_KEY`, and if that secret is unset the eval job
silently does nothing but the snapshot check. Both halves — a non-null
baseline and a live key in CI — are required for the gate to bite.

## Candidate gold set pipeline

The plan calls for failed production runs to auto-flow into a "candidate
gold set" for weekly triage by the operator.

**First-cut (this commit) — DRY RUN by default.**

- A debug-only endpoint `POST /api/debug/eval-candidate` accepts a JSON
  body `{ role, ticketId, finalText, expected, observed, notes }` and
  appends one JSON line to `tests/evals/candidates.jsonl`.
- The endpoint is gated by the `DEVPILOT_DEBUG_EVAL_CANDIDATES=1` env var; it
  returns 404 otherwise. It is NOT wired into the engine's failure
  handler by default. M12 leaves the wiring as an operator decision so
  the first cut is observable but cheap to back out.
- The file is **append-only** and **never read by the eval runner**. A
  human operator promotes entries into a proper `.eval.yaml` after
  triaging them. The file is `.gitignore`d (so PRs don't pollute it) and
  rotated by hand.

**Operator triage flow (weekly):**

1. Read `tests/evals/candidates.jsonl`.
2. For each line:
   - Reproduce: copy the `finalText` / `expected` / `observed` into a
     test case in the matching `<role>.eval.yaml`.
   - Strengthen: write an `llm-rubric` that would have caught the regression.
   - Add a regression-test entry to `baseline.json` (the new test joins the
     gold set's denominator).
3. Truncate `candidates.jsonl` after the triage.

**Why not auto-promote?** A flaky model day would silently grow the gold
set without operator review and lock in spurious failure modes. The plan
calls for manual triage explicitly.

## Hard constraints (do not edit without re-reading the plan)

- Promptfoo is a **dev-only dep** (`apps/web/devDependencies`). Never
  add it to runtime dependencies.
- All evals are **unit-level** against the prompt body — they MUST NOT
  call the live DevPilot engine, MCP runner, or any Inngest function.
- Model ID is pinned (`claude-sonnet-4-5-20250929`) and `temperature: 0`
  everywhere. Reproducibility > latest-model.
- A prompt edit changes BOTH the role source file AND the snapshot. A PR
  with only one of the two is a CI failure on the `snapshot-prompts.mjs
--check` step.
