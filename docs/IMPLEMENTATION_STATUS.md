## Current state (truthful)

Phase 0, Phase 1, and **most** of the Phase-2 plan have shipped, plus a large emergent **"Phase 2.5 / 2.5++"** surface that no planning doc formally defines.
The prior status docs badly understate this: `README.md` and `CLAUDE.md` (before this cleanup) still called the project "Phase 0 (MVP in progress)," and `SESSION_HANDOFF.md` freezes at 2026-06-11 while the branch shipped through 2026-07-05.

Concretely:

- **Phase 0** (durable engine + board + PM/Eng/QA + local CC runner + tracing): shipped. Two of the five named P0 _screens_ were never built — see the gap list.
- **Phase 1** (M0–M16: more roles, custom roles, parallel/branching, supervisor trees, SQL/text-to-SQL, marketplaces, evals + replay, agents-as-APIs + widget, billing, Agent Builder): shipped.
- **Phase 2 production plan** (M0–M4): only **M0** (stale-run reaper) and the emergent **M5 series** shipped. **M1, M2, M4 are not built**; M3 is partial. See the gap list.
- **Phase 2.5 / 2.5++** (undocumented): a large body of shipped work — take-the-wheel cockpit, platform secrets manager + app-layer AES, live tmux terminal attach, per-project repos + GitHub OAuth, plan-mode multi-agent chat, dev-servers, notifications, team tiers, stacked tickets, merger role, fail-closed budget breaker — exists only in git history and partial handoff rows.

The schema has grown from the ~12 core tables the TDD models to **~35 tables** across **54 forward-only migrations** (as of 2026-07-07), most for Phase 2/2.5 features the phase plans never enumerate.

## What's built (by area)

- **Work Board** — Kanban (dnd-kit) + dependency/DAG graph view (React Flow), blocks/blocked-by + Linear-style relations (`related`/`duplicate`/`builds_on`) + sub-issues, realtime agent+human comment threads, backward flow (QA/Security reject), schedules (recurring backlog drain), labels, a **first-run activation panel** (empty board → one-click starter tickets that seed straight into `Ready`; the same starters appear as presets in the New ticket dialog), a **first-dispatch nudge** (a one-time toast when the tenant's first-ever run comes into existence, deep-linking to that run's inspector; detection is a cheap engine-free `limit 2` probe in `lib/runs/first-run.server.ts` via a read-only server action, re-checked a bounded few times when the realtime stream shows a ticket entering a dispatched state; shown-once state is the `ace:board:firstRunNudge:<tenantId>` localStorage flag, set silently for tenants with existing run history), and **operator-cockpit affordances** (frontend-only, no schema changes): soft per-column WIP `count/limit` header pills that tip to a warning tone when exceeded (a Kanban heuristic - `in_progress` tracks the ~1-3 concurrent-agent runner boundary, `in_review` flags a review backlog - not a DB field); an optional **swimlane-by-role** grouping (off by default) with lanes derived from each ticket's last-comment author; a persisted compact/comfortable **density toggle**; a one-click **"Needs you"** filter chip that narrows to the `input_required`/`blocked` human-in-the-loop states via URL state (`attention=1`); and **keyboard-accessible drag-and-drop** (a dnd-kit `KeyboardSensor` + `sortableKeyboardCoordinates`: tab to a card's grip, Enter/Space to lift, arrows to move within and across columns, Enter to drop, Esc to cancel; the hover-reveal grip also shows on `focus-visible` so keyboard users get a visible focus stop). Motion is governed app-wide by a global `prefers-reduced-motion` guard in `globals.css` that collapses every animation/transition (Radix, Tailwind utilities, brand `dp-anim-*`, smooth scroll) to ~1ms - fast enough to read as static, but non-zero so `animationend`-driven Radix presence unmounts still fire.
- **Run Inspector** — the trace rendered as a timeline **waterfall** (default: proportional wall-clock duration bars, think→tool_call→tool_result grouped into collapsible turns, kind-colored bars, a cumulative cost curve toward the run's budget ceiling, and fan-out cohort siblings as inline lanes) with a **List** toggle to the flat step tree (think/tool_call/tool_result/human), per-step cost, Langfuse deep links, cohort + replay-chain navigators, **replay/time-travel** from any step, **live tmux terminal attach** (xterm.js over SSE), **take-the-wheel** interactive takeover, and a one-time **trace coach mark** ("This is the live trace") that marks itself seen on first render via the `ace:runs:traceCoachmark` localStorage flag.
- **Agent Builder** — React Flow visual editor, 6 node kinds + 3 edge kinds, undo/redo, round-trip to `agents.config`, test-run panel.
- **Roles** — **52 registered** built-in roles (PM/Engineer/QA/Security + specialists) + a **JD→role synthesizer** (drafts a `RoleConfig` over the tenant's LLM auth-mode: the local runner under `claude_code`, the direct API under `api_key`). Dispatch-time prompt composition runs through one seam, `composeRoleSystemPrompt` (`lib/roles/compose-prompt.ts`): a **reviewer-awareness note** ("your work is reviewed before it's accepted") for every ticket-bound run of a role whose `onSuccessStatus` is `in_review` - i.e. all but qa/verifier/release_engineer (self-drive to `done`), pm (`ready`), and triage (`in_progress`) - then the installed-skill fence. Both layers are fenced, idempotent, merged fresh at dispatch, and never persisted into `role_config.systemPrompt`.
- **Skill / Tool marketplace** — browse/install/uninstall/publish with verified first-party bundles.
- **Projects** — per-project GitHub repo + branches + team tier, **GitHub OAuth**, **per-project encrypted secrets vault** (AES-256-GCM), env catalog from `.env.example`.
- **Operator setup wizard + failure surfaces** — two-layer in-product credential management (2026-07).
  **Boot layer**: an unconfigured instance (no Supabase env) no longer crashes every request — middleware routes everything to a pre-auth `/setup` wizard, unlocked Jupyter-style by a one-time token printed to the server console (`instrumentation.ts`), which live-validates Supabase credentials, mints `SECRETS_ENCRYPTION_KEY`, and writes `apps/web/.env.local` through an allowlisted, comment-preserving, atomic writer (`lib/setup/env-file.ts`); the surface goes dead (403) the moment boot env exists. On serverless hosts (`VERCEL`) there is no writable env file, so the wizard degrades to read-only copy-paste guidance - no token, and the write/validate routes are hard-disabled (403).
  **Post-auth layer**: Settings → Setup (`/settings/setup`) walks every credential in dependency order — Supabase (read-only) → encryption key → Redis → Inngest → runner (one-click keygen + live connect detection) → LLM auth → GitHub OAuth app (dummy-code validation distinguishing bad-credentials from valid) → Langfuse → Stripe — each step guided, live-validated (tri-state: invalid blocks, unverified saves with a warning), and stored per design split D4: boot/infra/runner/Stripe keys → env file; LLM/GitHub-OAuth/Langfuse/`ENGINEER_*` → platform-secrets **instance scope** (no migration; the store already supported `tenant_id NULL`). Writes are gated on the instance-operator check (owner/admin of the first tenant). The platform-secrets resolver is now **default-on** (explicit `0` disables; store writes then error loudly).
  **Failure surfaces**: the auth callback emits structured `?auth_error=` codes; the login page renders friendly cards for them AND parses Supabase implicit-flow `#error=` hash fragments (config-class errors link "Fix in setup → `/settings/setup#github-oauth`"); the GitHub-integration page renders `?error_code=`; health probes attach per-service `remedy` links rendered as "Fix →" in the status popover and system-health cards (Langfuse probe is resolver-aware, so store-only keys probe green); `app/(app)/error.tsx` + `app/global-error.tsx` turn "Missing required env var: X" crashes into directed setup guidance.
- **Onboarding** — project-first guided `/welcome` flow (connect GitHub → create the first repo-backed project → **connect a runner**), opened by a compact **"Meet your crew"** framing of the PM→Engineer→QA→Security handoff (the shared `components/roles/handoff-diagram.tsx`, also rendered on the Agents page as "How the team works"), plus a step-0 "Finish instance setup" nudge for operators on installs missing required credentials, with a live "Waiting → Connected" indicator driven off the same system-health snapshot as the topbar dot. The board redirect is gated until a project exists **and** the runner step is satisfied — a heartbeating local runner, or an API-runner tenant (`expectsLocalRunner` false) that needs none. The New-ticket dialog soft-warns local-runner tenants when no runner is live so tickets aren't filed with nothing to pick them up. Because `/welcome` starts redirecting to the board the moment a project + runner exist (with the hardest step - the first run - still ahead), the same four checks also live as a **persistent, dismissible topbar readiness checklist** (GitHub / project / runner / first run): server-seeded for zero-flash first paint, live-refreshed from `GET /api/onboarding/readiness` on open/tab-focus/60s poll, and retired for good once all four pass or the operator dismisses (`ace:readiness:complete` / `ace:readiness:dismissed` localStorage flags, hidden pre-paint by an inline script). `lib/onboarding/readiness.ts` is the single owner of the derivation rules that the welcome screen, the topbar checklist, and the API route all share, so no two surfaces can disagree on what "ready" means.
- **LLM auth-mode** — explicit per-tenant choice (Settings → LLM auth) of which credential reaches Claude: `claude_code` (default — the local runner on the operator's own subscription, no API key) or `api_key` (per-token `ANTHROPIC_API_KEY`), stored in `tenants.config.llm_auth_mode`. A single resolver (`getLlmAuthMode`) drives runner routing (`decidePolicy`), onboarding runner-mode detection (`expectsLocalRunner`), and the auth-mode-aware system-health LLM probe (which reports not-applicable, never down, when no key is set under Claude Code auth). Server-side one-shot LLM features (JD role synthesis, dependency/data-source suggestion rankers, skill ranking) honor the same mode via `generateObjectForTenant` (`lib/llm/generate.server.ts`; pure routing core in `lib/llm/routing.ts`, subscription queue/poll bridge in `lib/runners/local-cc-oneshot.server.ts`), and every can't-proceed branch returns friendly copy pointing at Settings → LLM auth instead of the raw missing-env crash.
- **Plan mode** — multi-agent chat (3 parallel panels + consolidator) that commits to real backlog tickets with dependencies.
- **Dev-servers / workspace** — run-on-localhost dev-server launcher with stack detection + reapers, live git-driven file tree, and **changes / review-before-push** with split-diff review, conflict handling, and Push & PR.
- **Billing** — Stripe usage metering (Meter Events API), nightly aggregator cron, markup, soft-cutoff dispatch gate, billing portal.
- **Public platform** — v1 API (`POST /v1/agents/[id]/runs`, bearer `devpilot_*` keys, rate limiting, SSE), an **OpenAI-compatible** `/v1/chat/completions` shim, and an **embeddable widget** (iframe + scoped token).
- **Local CC Runner** — TypeScript worker: register + heartbeat, Redis job pull, isolated git workspace per ticket, `claude -p` spawn (subscription-only, API key stripped from child env), MCP board-tool relay, tmux live-attach, cancel channel, dev-server/takeover loops, auth-failure circuit breaker.
- **Platform layer** — Supabase Postgres with pervasive RLS multi-tenancy (~35 tables), app-layer AES-256-GCM secrets (DB never sees plaintext), platform secrets manager, system-health probes (7 dependencies), text-to-SQL query-as-tool with all four guardrails (its natural-language "smart" mode is API-key-mode-only: it runs inside an in-flight runner job, so it can't nest back through the runner; direct-SQL mode works under either auth-mode), budget ceilings + fail-closed cost-velocity breaker, engine self-healing for stranded tickets (post-completion ticket reconciler + stuck-ticket sweeper cron - `lib/engine/reconcile-policy.ts` / `ticket-reconciler.ts` / `stuck-ticket-sweep.ts`) **and stranded dev-server sessions** (fail-forward-to-`errored` reconcile via the runner-watchdog + `devServerReaper`, decided by the pure `lib/engine/dev-server-reconcile-policy.ts`), and **25 registered durable Inngest functions**.
